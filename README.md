# Тестовое Neowise. AI-помощник для входящих заявок

Ориентир — 45–60 минут. Менеджер вводит текст заявки, получает тему и черновик ответа. Он читает результат и сам решает, что отправить клиенту.

## Запуск

В репозитории есть сервер, HTML-страница и имитатор модели. Нужен Node.js 20 или новее. Зависимостей и ключей нет.

```sh
node server.mjs
```

Откройте http://127.0.0.1:3000. Порт можно задать через переменную `PORT`.

## Тесты

Из корня проекта:

```sh
node --test
```

Нужен Node.js 20+. Установка npm-пакетов не требуется. Тесты поднимают HTTP-серверы на свободных локальных портах и сами их закрывают.

## Реализованное поведение

- Ввод проверяется до обращения к модели: битый JSON, отсутствие `text`, неверный тип и строка из пробелов дают `400 {"status":"invalid_input"}`.
- В `server.mjs` после разбора JSON проверяется смысл результата: тема входит в `delivery`, `pricing`, `other`, а `draft.trim()` не пуст. В API попадают только явно разрешённые поля.
- Ожидание модели ограничено 300 мс через `Promise.race`. `AbortController` дополнительно отменяет работу имитатора; таймер очищается в `finally`. Если провайдер игнорирует отмену, API всё равно перестаёт ждать.
- Любой предусмотренный сбой модели возвращает **HTTP 200** и `{"status":"manual_review","topic":null,"draft":null}` — это бизнес-результат по контракту задания, а не успешная генерация.
- Интерфейс показывает понятную тему, редактируемый черновик и сообщение о статусе. При сбое менеджер видит «Нужен ручной разбор», исходная заявка остаётся в поле ввода, предыдущие тема и черновик очищаются. Отправки клиенту на странице нет.
- Старый черновик очищается уже при новом запросе или изменении исходного текста. Поздние ответы и ошибки устаревшего запроса игнорируются по идентификатору запроса. Предыдущий HTTP-запрос также получает сигнал отмены.
- Ошибки сети, HTTP, некорректный ответ API и ожидание API дольше 5 секунд также переводят интерфейс в ручной разбор. Клиентский таймаут охватывает и чтение тела ответа.
- Текст выводится через `textContent` и `value`, без вставки AI-ответа как HTML. Имитатор `mock-ai.mjs` не изменён.

### Быстрая проверка в браузере

1. Отправьте «Когда доставка?» — появятся тема «Доставка» и черновик.
2. Следом отправьте `[bad-topic]`, `[empty-draft]`, `[bad-json]`, `[error]` или `[timeout]` — получите ручной разбор, пустой черновик и тему «—».
3. Введите только пробелы — увидите просьбу заполнить заявку; обращения к модели не будет.
4. Измените исходную заявку после успешного разбора — черновик предыдущей заявки сразу очистится.
5. При ручном разборе можно самостоятельно написать текст в поле черновика. Он существует только на текущей странице; сохранение в БД и отправка клиенту в задании не реализуются.

### Что проверяют исполнимые тесты

`test/triage.test.mjs`: 46 проверок реального HTTP API и контроллера интерфейса. Покрыты все пять маркеров сбоя, успешные темы, неверные входные данные и ответы модели, отмена по таймауту, провайдер без поддержки отмены, очистка старого черновика, сетевые/HTTP/JSON-ошибки и обратный порядок ответов. Гонки проверяются управляемыми Promise, без случайных задержек.

### Использование AI и контроль результата

Для анализа, реализации и подготовки тестов использован Codex. Отдельная проверка результата включает запуск `node --test`, сверку ответов с исходным контрактом и просмотр diff: имитатор сохранён, workflow-статус не берётся из ответа модели, отказ не оставляет предыдущий черновик. Логи тестов подтверждают исполнение сценариев; тесты контроллера не заявляются как полноценный браузерный E2E-набор.

### Польза менеджеру и измерение

Менеджер получает пригодный черновик либо явный переход к ручному разбору, без риска принять старый ответ за результат новой заявки. Улучшение можно измерить временем обработки одинаковых учебных заявок, долей ручных исправлений и количеством случаев показа устаревшего черновика; фактическая экономия времени пока не измерена.

## Что изменить

1. Доработайте `POST /api/triage`. Принимайте JSON с полем `text`, содержащим непустую строку. При пустом, отсутствующем, нестроковом вводе или битом JSON верните HTTP 400 и `{"status":"invalid_input"}`.
2. При корректном ответе модели верните HTTP 200 и `{"status":"ready","topic":"…","draft":"…"}`. Допустимые темы — `delivery`, `pricing`, `other`. Черновик должен быть непустой строкой. При таймауте, ошибке модели или неподходящем ответе верните HTTP 200 и `{"status":"manual_review","topic":null,"draft":null}`. Ограничьте ожидание модели 300 мс. Оставьте поведение выданного имитатора прежним.
3. Покажите на странице тему и черновик при успехе. Для `manual_review` покажите понятное сообщение менеджеру и очистите предыдущий черновик. Добавьте хотя бы один исполнимый тест для поведения при сбое и инструкцию его запуска.

Для локальной проверки имитатор принимает любой обычный текст. Метки `[timeout]`, `[error]`, `[bad-json]`, `[bad-topic]`, `[empty-draft]` включают отдельные сценарии сбоя.
